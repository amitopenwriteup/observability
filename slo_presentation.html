Why SLOs Matter

SLOs bridge the gap between engineering reliability and business objectives, providing quantifiable targets that align technical performance with user expectations.

Slide 1 of 12

📚 Core SLO Terminology

SLI

Service Level Indicator

A quantitative measure of service behavior

Example: Request latency, error rate, system throughput

SLO

Service Level Objective

Target value or range for an SLI

Example: 95% of requests < 200ms

SLA

Service Level Agreement

Business contract with consequences

Example: 99.9% uptime or credit issued

Error Budget

Allowed Downtime

100% - SLO = acceptable errors

Example: 0.1% = 43 min/month

Slide 2 of 12

🔺 The SLO Hierarchy

SLA (Business Contract)
↓
SLO (Internal Target)
↓
SLI (Measurement)

Relationship Example

  • SLA: We promise 99.9% availability to customers (with penalties)
  • SLO: We target 99.95% availability internally (buffer zone)
  • SLI: We measure uptime using successful health checks / total checks
SLA ≤ SLO = f(SLI)

Always set SLOs stricter than SLAs to provide safety margin

📊 Common SLI Categories

Category SLI Examples Measurement Method
Availability Uptime percentage, successful requests Successful probes / Total probes
Latency Response time, processing duration 95th percentile response time
Quality Error rate, data accuracy Failed requests / Total requests
Throughput Requests per second, bandwidth Requests processed / Time period
Durability Data retention, backup success Data retained / Data stored

💡 Pro Tip

Choose SLIs that directly impact user experience. Technical metrics like CPU usage are useful but should be secondary to user-facing indicators.

Slide 4 of 12

✅ Defining Good SLOs

1. User-Centric Focus

Define SLOs from the user's perspective, not internal system metrics

2. Measurable & Achievable

Must be quantifiable with existing tools and realistically attainable

3. Business-Aligned

Support business objectives and customer satisfaction goals

4. Actionable

Clear actions when SLO is at risk or violated

Common Pitfalls to Avoid

  • Setting SLOs too aggressive (100% uptime is unrealistic)
  • Measuring too many SLIs (focus on what matters)
  • Internal-only metrics with no user impact
  • Ignoring cost of maintaining high SLOs

💰 Error Budgets in Action

What is an Error Budget?

The amount of unreliability a service can accumulate before consequences occur. It's calculated as 100% - SLO% and represents allowable downtime or errors.

Error Budget = (1 - SLO) × Time Period
SLO Target Error Budget Downtime/Month Downtime/Year
99.9% (3 nines) 0.1% 43.2 minutes 8.76 hours
99.95% 0.05% 21.6 minutes 4.38 hours
99.99% (4 nines) 0.01% 4.32 minutes 52.6 minutes
99.999% (5 nines) 0.001% 26 seconds 5.26 minutes

Use error budgets to balance innovation vs reliability: Budget remaining = deploy new features. Budget depleted = focus on stability.

🐧 Linux Host SLO Implementation

Sample SLOs for Linux Hosts

SLI Measurement SLO Target Dynatrace Metric
Host Availability Uptime percentage 99.9% builtin:host.availability
CPU Performance CPU usage < threshold < 80% for 95% of time builtin:host.cpu.usage
Memory Availability Free memory available > 15% free memory builtin:host.mem.available
Disk I/O Latency Read/write latency < 20ms for 95% requests builtin:host.disk.readTime
Network Performance Packet loss rate < 0.1% packet loss builtin:host.net.packetsDropped

✅ Do This

  • Monitor user-facing services
  • Set realistic thresholds
  • Use percentiles (p95, p99)
  • Review SLOs quarterly

❌ Avoid This

  • 100% availability targets
  • Too many competing SLOs
  • Internal-only metrics
  • Static, never-reviewed SLOs
